# Does low CPU justify reviewing a container's request?

Start with the CPU panel you already use. If it shows the workload is holding approved failover capacity and the owner confirms that is still needed, record **retain** and stop. Otherwise compare CPU used with CPU requested for **one container in one named Pod**. This is an investigation, not a sizing calculation.

## Try the fictional case without any tools

Open the [saved report](../../examples/expected-source-ordinary.md). Over its fixed observation window, the named container's P95 usage was **100 mCPU** and its P95 request was **1,000 mCPU** (one CPU core). Both source series returned all expected evaluation points. The workload check still reports 0% metric coverage: the names do not establish which historical Pod and workload owned those samples. Neither number is a replacement request.

Ask the owner: **Does an HPA scale on CPU utilization, and does this window include peak or failover demand?** For that kind of HPA, reducing the request can raise reported utilization even if usage stays flat. If either answer is unknown, retain the setting and record who can check it. These CPU queries do not read HPA configuration.

## Use your existing Grafana or Prometheus

For cluster-wide context on **Azure Monitor managed Prometheus**, import the [cluster efficiency dashboard](../../deploy/grafana/aks-cluster-efficiency.json) in Grafana. Choose the same **Data source** as the built-in **Kubernetes / Compute Resources / Cluster** dashboard, then select an approved alias from **cluster**. This picker uses the same Grafana `label_values(up{job="cadvisor"}, cluster)` query as the built-in dashboard. Use an alias the monitoring owner has mapped to the approved Azure resource ID, not a resource ID typed into the picker. If the picker is empty, check the selected datasource, time range and `up{job="cadvisor"}` in Grafana Explore. If a panel is empty, use **Inspect → Query** to check the resolved query. Do not remove the cluster filter.

To drill down, select **Namespace**, then **Pod**. The pickers use `kube_pod_info` and inherit the selected cluster and, for Pods, the selected namespace. The namespace panels show totals for that namespace; the Pod panels show totals for the selected Pod. A blank selection or absent series stays unknown. If you change clusters or namespaces, check the dependent selections before comparing panels.

The selectors are not authorization boundaries: use a datasource whose whole query scope is authorized for its users. The [Azure default metric reference](https://learn.microsoft.com/azure/azure-monitor/containers/prometheus-metrics-scrape-default) lists the required raw metrics; this dashboard does not require the built-in dashboard's recording rules. It shows observed capacity, allocatable resources, regular-container request gauges, and cAdvisor usage, not effective Pod reservation, safe changes, or savings. Confirm expected series and the absence of duplicate scrape targets before interpreting totals. Pod names may be reused and are not stable workload identities. Use the steps below for a single-container investigation.

If the workload already has an HPA, use [Rightsizing & Scaling Review](../../deploy/grafana/aks-rightsizing-scaling-review.json) before comparing requests. Import it as a separate dashboard and choose the existing **Data source**, then **Cluster → Namespace → Horizontal Pod Autoscaler**. Start with six hours around a known demand or deployment change. The selected namespace and HPA must appear in Prometheus; if the HPA picker is empty, check `kube_horizontalpodautoscaler_status_desired_replicas` in Explore for the approved cluster. Do not remove the cluster or namespace filter to make a panel populate.

- **Replica counts and bounds:** Compare observed desired/current replicas with configured min/max. Use the UTC view and the tabular legend to distinguish traces that overlap. Current is not Ready or Available. A positive signed gap means fewer current replicas than desired; it does not explain the gap or measure time to Ready.
- **Bound state:** Individual evaluation points report `0` not pinned, `1` at floor, `2` at ceiling, or `3` fixed. A bound requires both counts to equal it; all four gauges must match at the evaluation point. Missing, invalid or duplicate series leave gaps, not zeros. The dashboard neither sums duplicates nor arbitrarily selects a replica of the scraper. Check Query Inspector when a series drops out. Samples can reflect Prometheus lookback and are not evidence of continuous behavior or UID-bound workload history.
- **Before changing requests:** Check the actual scale target and metric type in approved Kubernetes metadata. The rule guide covers [HPA/VPA overlap and bound review](../metrics-and-scoring.md#current-autoscaler-interaction). This Grafana view does not show the controller's actual scaling signal, infer VPA targets, predict replicas, or approve changes. Return to the native workload dashboards for CPU, memory, and other demand signals until an approved source supplies that binding.

For deployment validation, import to the approved demo folder, rebind the datasource, and inspect one real HPA in the default six-hour UTC window. Switch to a different namespace or an approved empty selection; values from the previous namespace must disappear. With the approved denied identity, confirm the query is denied rather than displayed as a healthy zero. Record the Grafana version, dashboard revision, resolved selectors and UTC window. This check is separate from the [protected fleet evidence snapshot](../fleet-insights.md#export-a-protected-grafana-evidence-snapshot).

### Investigate one container

1. Open the [starter files](../../examples/cpu-starter/). On GitHub use **Download raw file** for the [dashboard JSON](../../examples/cpu-starter/dashboard.json), or open the [usage query](../../examples/cpu-starter/cpu_usage-22d8565a085fca3fe6b855943ee34efd8f06c6cea19a44bb19b72cb6a74b8bdd.promql) and [request query](../../examples/cpu-starter/cpu_request-22d8565a085fca3fe6b855943ee34efd8f06c6cea19a44bb19b72cb6a74b8bdd.promql) as text. No CLI, new datasource or recording rules are required. The files use fictional exact selectors; they are not preconfigured for your cluster.
2. Have the monitoring owner confirm that both metrics carry the full Azure cluster resource ID plus namespace, Pod and container labels. A cluster display name is not that ID. In Grafana **Explore**, paste each query and replace those four quoted values with one approved scope. Change label keys only if the owner has confirmed their meaning. Keep exact `=` matches and the request's resource and unit filters. If a required label is absent, stop rather than removing the filter.
3. Select the approved datasource and the same bounded time range for both queries. Expect a five-minute CPU usage rate and a CPU request gauge, both in millicores, not percentile curves. Check for one matching series per query. Multiple series require disambiguation; an empty result means unknown, not zero. Check scope, metric availability and retention before interpreting it.
4. To use panels instead, have the dashboard owner adapt the same exact selectors in a **local copy** of the two JSON target expressions before import. Use **Dashboards → Import**, upload the copy and bind `DS_PROMETHEUS` to the approved datasource. The quality panel describes the fictional export, not the customer's datasource; the [manifest](../../examples/cpu-starter/manifest.json) applies only to the original files. Keep customer-scoped copies in approved storage, not this repository. Explore does not require saving a dashboard.

Read the mCPU values at the same timestamp; do not compare the lines' heights across panels. Grafana can scale each y-axis independently, so 100 mCPU and 1,000 mCPU can appear at the same height. If a long series label is clipped in the panel, check the exact labels in Explore before recording the observation.

Record the source, time range, units, missing evidence, owner and next decision in your existing review ticket or the [worked workbook](../facilitator/participant-workbook.md#worked-exercises). If a repeatable assessment is needed, follow the [optional ordinary-source walkthrough](../source-profiles.md#ordinary-telemetry-without-invented-history); it also documents how the starter export is reproduced. No billing import, model disclosure or production change is part of this investigation.
