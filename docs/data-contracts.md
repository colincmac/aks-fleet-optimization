# Data contracts

## Unified Version

Advisor-owned assessment, snapshot, collection, financial and handoff contracts use **schema 1.0**. All 25 recommendation packs, shared query assets and source profiles use **1.0.0**; the original 24 packs remain the defaults and `AKS-START-001` is opt-in. Sanitized financial projection tags use their `-v1` forms. These are first-revision internal formats, not a production-readiness claim or a package release; the unreleased package remains `0.1.0`. Native/API, producer, dataset, dependency and pinned-tool versions retain their independent meanings and are not reset.

Earlier unreleased advisor formats have no compatibility reader, alias or migration. Keep the matching package for replay of a pre-reset bundle, or create a new assessment from separately reviewed original evidence. Never edit stored hashes, locks or source declarations to make an old bundle appear current. Inputs must use a supported schema and configuration; unsupported schemas are rejected. The [JSON schemas](../schemas) are generated by `scripts/generate_schemas.py`; `--check` detects drift without writing. JSON Schema alone does not enforce executable scope, projection, receipt, UTC and cross-field validations.

Every rule ID in `AnalysisReport` must have a manifest, and selected findings use that manifest's version. `PackManifest` owns evidence-selected controller `summary_variants` (closed, evaluator-specific keys) and CPU `baseline_rollback` guidance. These are local text, not executable expressions. Configuration locks must match installed manifest and query definitions. When they differ, retain a compatible package for replay or create a new assessment from reviewed original evidence; never edit saved hashes to conceal the mismatch.

## Pack Selection And Replay

All 25 rules have closed typed evaluators and manifests, including eight memory/reliability packs. Memory policies remain owner-only bounds; these packs forbid ratio parameters. Current accounting and termination are inventory-only. OOM/restart, memory usage/request/limit, replica-envelope and workload reliability/controller references share packaged query assets with explicit MiB/events/pods/boolean units.

`RuleAssessment` retains each rule's own required metrics, quality map, evidence, reason codes and signal. Shared scope/quality gates remain outside family algorithms. Unsupported source-profile checks apply to numeric proposals, and baseline still rejects any numeric proposal. Source/wheel replay preserves the exact original request/limit/accounting shapes; no schema compatibility reader or source attestation is introduced.

Manifests use closed evaluator/family/evidence bindings. `PackParameters.review_ratio` is required only by CPU request review, CPU request risk and pool review, with their own finite bounds. Inventory and memory/reliability evaluators forbid a ratio; memory proposal bounds belong to owner policy. Inventory manifests declare no transports or queries. Metric manifests require nonempty entity-specific dependencies for both modes and all manifests require explicit operator actions/validation/rollback.

Missing request, request risk and pool review use version 1.0.0 and propose neither resources nor savings. Node query assets retain mCPU/MiB units and exact historical node identity. Current-only membership or changing capacity remains unsupported by the existing sum-before-percentile normalization. The identity-enriched source profile uses version 1.0.0 for node, memory/ reliability, workload guard and HPA history references. Source capabilities do not pretend that inventory requires Prometheus.

See [recommendation packs](recommendation-packs.md). `AdvisorConfig.mode` defaults to `baseline`; `guarded` is explicit. Optional `packs` is a nonempty distinct list of implemented pack IDs; omission evaluates the original 24 default packs, while startup remains opt-in. The scheduling, optimization-constraint, capacity, NAP consolidation-readiness and DaemonSet overhead inventory packs provide qualified investigations or explicit missing-context blocks, not numeric proposals. An incomplete installed catalog is rejected rather than executing an unpacked rule. Pack parameters are typed, bounded and per-pack. For CPU request review, configure `pack_parameters.AKS-RQ-002.review_ratio`.

`AnalysisReport` requires mode and selected pack provenance. Its validator rejects baseline numeric proposals. Provenance includes pack version, manifest/query digest, parameters and query definitions. `MetricQuality` retains optional `query_expression` from actual collection; omitted import provenance stays unknown, never inferred from current definitions.

`AnalysisSummary.pack_subject_counts` records examined subjects separately for every selected pack, including blocked and no-finding evaluations after namespace exclusions. Units follow the evaluator: cluster capacity scopes, NAP pools, DaemonSet controllers, Pods/PDBs, ARM pools, workloads or containers. Missing subject inventory does not synthesize subjects, and counts are not additive across packs or proof of complete inventory. The older workload/pool totals describe snapshot vertical-workload/ARM-pool records, not all selected-pack subjects. Inventory-only reports retain metric-window diagnostics as explicitly independent context; overall partial collection remains visible while each finding keeps its required-source gates.

The [fleet drift matrix](fleet-insights.md#project-a-fleet-drift-matrix) projects these counts and replayed findings, blocker records, and severity counts per selected pack without changing the report or comparisons. A blocker can describe inventory that was missing before any subjects could be examined. The expected subject roster is not retained, so these independent counts cannot be divided to derive check coverage.

Artifact exports save effective `pack_locks`; configuration validation and analysis reject mismatches before live access or evaluation. A hash binds definitions, not customer source attestation or change approval. Fixed-clock source/installed-wheel replay uses the same evidence, parameters and assets.

## Snapshot Contract

Preserve exact subscription/cluster/agent-pool Azure IDs and cluster fingerprint, Namespace/workload/Pod/node UIDs. Names are display fields, not substitutes for historical identity. All timestamps must be aware and normalize to UTC. Windows are ordered; numeric values are finite and unit-labelled. Missing, zero and explicitly absent are different states.

`FleetSnapshot.collection_manifest` may be missing only as incomplete evidence: rules then block. `ResourceObservation.cpu_request_observed` defaults false. Omitted HPA/KEDA/VPA/OOM state is unknown, never false/zero. `cpu_observation_basis` must explicitly be `pod` or `replica-envelope` before numeric CPU proposals; unknown aggregation blocks them.

`ResourceObservation.memory_request_observed` and `memory_limit_observed` default false. Values and flags describe current admitted evidence only; historical quality is separate. Unknown, observed absence and observed zero are not interchangeable.

## Scoped Collection Eligibility

Every manifest requires nonempty `source_results` and one `results` aggregate per collector. Aggregates must exactly match deterministic source merges, including clocks, retries, pagination, missing fields, failures and status. Overlapping sources, contradictory completion and missing receipts are rejected. Unknown source clocks stay unknown.

Each `CollectorResult` records nonempty requested scope, completed subset, UTC collection clocks, optional source observation time, pagination, retries, missing fields and sanitized failure codes. Complete requires every requested scope, all pages, no errors and no missing fields. Failed requires an error and no completed scope; incomplete fragments stay partial/failed.

Rules select exactly one complete, fresh, temporally valid matching source for each required collector. Azure matches exact cluster or subscription; Kubernetes and metrics match the exact cluster. Ambiguity blocks. A partial multi-scope receipt cannot be split into successful completed scopes. Optional cost failure does not suppress capacity findings. Global sample/coverage floors are diagnostics; required entity-level quality remains a hard gate. Independent healthy findings can coexist with denial and overall partial status.

## Kubernetes Metadata

Metadata carries exact cluster scope, an independently approved `kube-system` Namespace UID fingerprint, API availability/list versions, projected objects, ownership and node-provider reconciliation. The fingerprint is operational binding evidence, not Azure attestation. Export ingestion reruns the collector's allowlist projection and rejects unsupported kinds, attributes, labels or nested fields before persistence.

Approved projections retain requests/limits, init/sidecar/runtime overhead, scheduling constraints, HPA targets, VPA policies/status and PDB details. Typed `OfflineAssessment.metadata_evidence` retains them for later rules without flattening unknowns into booleans. Pod environments/commands/arguments/annotations, Secrets, ConfigMap bodies, logs, private addresses and credential material are excluded. Only named labels are retained; dropped labels are unknown, not absent.

Available APIs need successful versioned lists; absent must be explicitly discovered absent, not denied/unsupported. Ownership follows exact namespace/API/kind/name/UID references through ReplicaSets where applicable. Node-provider joins require approved Azure parent/pool/resource-group bindings. Cross-resource lists are not transactional. The SDK may transiently decode excluded fields before projection; operators requiring a stricter boundary must supply approved sanitized readers/exports. See [Kubernetes operations](operations/runbook.md#kubernetes-metadata-api).

### Optional Current Container Attempts

SDK `project_current_container_attempts(metadata_snapshot, native_pod)` returns schema-1.0 `PodContainerAttempts` from an already approved `KubernetesMetadataSnapshot` and separately supplied core/v1 Pod dictionary. It performs no I/O and does not change default collection, sanitized metadata exports, assessment assembly, rule eligibility or CLI output. The [standalone schema](../schemas/pod-container-attempts.schema.json) is separate from the metadata-fragment schema.

The projector revalidates the sanitized metadata allowlist, requires exact projected Pod equality, distinct Namespace identity, the original `kube-system` fingerprint and the existing UID-resolved workload owner chain. It preserves tenant/cluster/Namespace/Pod bindings, nullable workload UID, the original collection receipt and `metadata_generated_at`. The native payload supplies nullable Pod `creationTimestamp`/`resourceVersion` and regular container status `name`, strict nonnegative integer `restartCount`, current state and `state.running.startedAt`. Only a SHA-256 digest of `containerID` leaves the projector; messages, images, ready/started flags, handlers and raw IDs are discarded. Containers are sorted by name; inputs remain unchanged. This first adapter is not an ingestion path for arbitrary saved context files.

The mapping reference is Kubernetes core/v1 definitions at v1.36.0, the minimum reference baseline for new Kubernetes field research, not detection or certification of the caller's producer version. Running `startedAt` is the last (re-)start, and a restart counter can reset after kubelet state loss. `pod_to_attempt_start_seconds` is strictly the supplied current-running-start minus Pod creation, not initialization latency. For example, creation at 11:00Z and current start at 11:55Z produce 3,300 elapsed seconds even with restart count zero; they do not prove a first attempt or 55-minute application startup. Equal creation/start yields observed elapsed zero, not zero application startup duration.

Missing lifecycle fields remain null with machine issues. Missing/waiting/terminated status cannot provide a running start; duplicates, foreign containers, ambiguous states, malformed counters and contradictory/naive/future clocks are rejected. Partial receipts and old/missing source clocks are retained, never refreshed or qualified. `supplied_payload_observation_unverified` and `metadata_freshness_unassessed` always remain explicit: matching identity and approved fields cannot prove that the separately supplied payload shares a collection transaction, observation clock or resource version with the sanitized snapshot, which does not retain per-Pod versions. The generated-at clock only bounds internally consistent supplied timestamps; it is not the native Pod's independently observed time.

`first_startup` is fixed to `unknown`; `application_startup_duration_seconds` and `post_startup_demand` are fixed null. Readiness, startup peaks, complete restart history and a distinct representative post-startup window are not established. A characterized lifecycle-history producer, episode/window admission, assessment integration and a bounded investigation pack remain unfinished. See the [pinned native field definitions](https://github.com/kubernetes/kubernetes/blob/v1.36.0/staging/src/k8s.io/api/core/v1/types.go) for the mapping baseline, not a live-source acceptance claim.

### Saved Startup Investigation

`project_startup_history` consumes separately approved saved `(KubernetesMetadataSnapshot, native Pod)` frames and emits [StartupHistoryEvidence](../schemas/startup-history.schema.json). It does not collect history or create a resident observer. The adapter reuses the Kubernetes v1.36.0 current-attempt projection and additionally retains only a closed Pod Ready condition state. Original metadata digests, receipts, sample clocks, exact tenant/cluster/fingerprint/Namespace/workload/Pod/container identities and digested runtime IDs remain bound. Raw status messages, runtime IDs, handlers, annotations and environment values never enter the result.

The contract describes a **sampled Pod readiness proxy**, not first-ever startup or application initialization. The first supplied sample must be explicitly not-ready, a later sample ready, and later samples must stay ready. The Pod creation clock and sampled runtime digest/restart count/running-start tuple must remain identical. Every declared grid point is required; missing/duplicate/unknown states, changed attempts, incomplete sources, future/stale clocks and left-censored readiness block the affected interval. Same-resourceVersion contradictory observations are rejected. Zero restart count does not establish a first attempt, and samples cannot exclude an unobserved between-sample restart/readiness change. `first_startup` remains unknown and application duration remains null.

The lower/upper elapsed seconds are the preceding not-ready sample and first ready sample, respectively, minus supplied Pod creation. They bracket an observed transition, not necessarily the first transition since creation. Source binding remains unverified saved native observations; exact JSON, receipt and digest agreement does not authenticate a source, independently establish field observation time or certify producer completeness. The adapter is synthetically tested, not a declaration that kube-state-metrics gauges provide complete lifecycle history. ## Optional saved controller timeline

The [controller-evidence schema](../schemas/controller-evidence.schema.json) (`schema_version: "1.0"`) and `qualify_controller_timeline` SDK function accept a reviewed saved projection for **one Deployment, one HPA, and one CPU `Resource`/`Utilization` signal**. The caller supplies the independently reviewed scope and window, an explicit aware evaluation time (`as_of`), and a maximum age. Every observation must bind exactly to the expected tenant, AKS resource ID and cluster fingerprint (`cluster_uid`), Namespace/Deployment/HPA UIDs, signal descriptor, and reviewed producer identifier. No name-based joins, multi-metric attribution, or inference from `HpaReplicaHistory` extrema are supported.

| Series | Meaning at the original observation time |
| --- | --- |
| `signal` | CPU utilization percentage actually reported by the HPA for the admitted metric; integer, zero allowed and not capped at 100% |
| `target` | Independently observed configured utilization target in percent; positive integer |
| `hpa_replicas` | HPA desired/current counts from status; neither is Deployment readiness |
| `request_mcpu_per_pod` | Optional positive mCPU value for the CPU request basis actually shared by all Pods in the admitted HPA measurement scope; omit if missing or heterogeneous |
| `deployment_availability` | Optional independently observed Deployment Ready and/or Available counts; distinction and true zero preserved |

Use the reviewed `[start,end)` UTC grid (1–1,440 slots; step 1–3,600 seconds). Each sample retains original `observed_at`, distinct `captured_at`, both configuration and request-basis revisions, and an opaque `observation_ref` to approved original evidence. Capture time cannot precede observation or be after evaluation. Do not copy the same latest status to several slots, use scrape/capture time as the missing signal observation time, round measurements to the grid, or apply current requests, workload identities, or readiness to older slots. HPA and Deployment samples aligned at one evaluation point do not establish transactional capture or causality.

`qualified` requires all three HPA series at every slot, a complete source receipt declared by the reviewed producer, and a fresh latest observation for each required series. Age equality passes. `segmented` meets the same requirements but marks the start of each contiguous revision pair; never compare across configuration or request-basis segments as if they were unchanged. Optional context is usable only at its matching slot; a qualified HPA timeline does not imply request or readiness coverage. `partial` preserves usable observations, reports matched/expected HPA slots, and returns no qualified segments; a mixed-revision slot is unknown. A foreign scope, unreviewed window, duplicate or off-grid observation, impossible clock, inconsistent target or request value under the same revision, stale evidence, or partial/denied source receipt returns `blocked` with a closed reason and no points. Malformed input is rejected rather than inferred.

The timeline is SDK-only; it is not part of assessment bundles, existing rule admission, Grafana panels, Headlamp feeds, or AI exports. `qualified` describes structural alignment of reviewed inputs, not source authentication, representative demand, sufficient reliability, or permission to change resources. See [producer review requirements](source-profiles.md#review-a-saved-controller-source).

A zero difference does not establish that the correct Nodes are covered. The review finding includes exact-bound coverage context and separately labeled known counters without making status availability an additional gate for independently valid request-share evidence. Full desired membership/protection, storage/domain eligibility and active disruption interpretation remain unimplemented.

Require Manual provisioning, observed pool metadata, exact current and approved historical node membership, constant full-window `mCPU`/`MiB` allocatable totals agreeing with node totals, and aligned sum-before-percentile pool CPU usage. Pool capacity is a total, not a per-node value. Never substitute current allocatable values, sum percentiles, extrapolate survivors or invent count/mode/Spot flags. NAP, churn and changing capacity remain explicit unsupported cases, not removable-node or savings claims.

## Current Workload Inventory

Support `apps/v1` Deployment/StatefulSet with 1 to 100 declared replicas, exactly that many distinct Running v1 admitted Pods, exact Namespace/controller chains, versioned APIs and conservative PDB evidence. Every Pod must have identical normalized container names, CPU requests, memory requests/limits and observation states. Mixed/currently incomplete populations stay unsupported rather than being represented by one arbitrarily selected Pod. Evidence retains every current Pod UID deterministically as `current_only`; Running does not imply readiness or historical membership.

Requests come from admitted Pods, never templates. Explicit empty requests/null CPU establishes observed absence; omitted requests remain unknown. Present string quantities use `kubernetes.utils.quantity.parse_quantity`, lazily loaded from the optional extra, converted from cores to mCPU. Invalid, negative, nonfinite, overflowing and underflowing values fail closed. Parser absence is a gap. Inventory alone may support missing-request investigations, but cannot supply usage, autoscaler absence or owner policy.

Memory requests and limits use the same quantity parser, converting bytes to MiB (1 MiB = 1,048,576 bytes). Binary/decimal suffixes and exponent notation retain their standard meanings. An explicit resources `requests`/`limits` map with an omitted or null memory entry establishes observed absence (`true` flag, null value), not zero. Omitted maps remain unknown (`false` flag); explicit zero is retained as zero. Malformed, negative, nonfinite, overflowing or underflowing memory quantities leave that memory field unknown without fabricating a value or discarding valid CPU evidence. No admission defaults or values from templates are inferred.

## Single-Pod History

`workload_assessments` binds tenant, exact cluster/fingerprint, Namespace/workload identities, a duplicate-free `pod_uids` historical roster, source, history reference and explicit `WorkloadSafetyPolicy`. Bindings cannot transfer to recreated identities. Current members must be in the historical roster. References are not fetched/executed; they and policy are declarations, not source attestation or change approval.

For exactly one current replica and one historical Pod, consume that Pod's issue-free CPU percentiles/extrema, request history, maximum throttling and complete zero OOM interval total. Desired/available replicas and request must be constant across the full aligned grid. HPA/KEDA/VPA histories must explicitly be zero and independent successful current API evidence must prove absence. All current Pods need explicit empty initContainers/overhead and null runtimeClassName. Missing evidence is not absence.

## Replica Envelope History

For multiple replicas or a churned historical roster, require approved upstream `workload_container` recordings. Their `membership_digest` is SHA-256 of canonical sorted JSON containing cluster resource ID/fingerprint, Namespace UID, workload UID and sorted historical Pod UIDs. Every aggregate selector carries that digest. The roster includes deleted members; current Pods alone cannot establish it. Digest/reference assertions require an approved producer and do not cryptographically attest source completeness.

| Catalog Key | Required upstream meaning |
| --- | --- |
| replica_cpu_envelope | Aligned maximum CPU mCPU across the approved roster at each point |
| replica_cpu_request_min / replica_cpu_request_max | Minimum/maximum observed request across active members, both constant at the current admitted request |
| replica_cpu_throttling | Aligned maximum per-container throttling ratio across members |
| replica_oom_events | Complete per-step OOM increase across members, zero required |
| observed_replicas | Explicit observed member count, constant at declared desired/available replicas |

The collector computes percentiles from aligned **maximum-replica-envelope samples**. These are conservative per-replica upper-envelope statistics, not actual workload-total percentiles or averages of Pod summaries. Full aligned coverage, current homogeneous requests, exact digest, stable observed/desired/available count, complete controller histories and independent current absence are mandatory. Request/replica changes, mixed identity and unsupported lifecycle semantics stay blocked; no survivor extrapolation or automatic time-segmentation is attempted.

## Workload Safety Policy

Numeric CPU reductions require owner, SLO reference, exact reviewed UTC window, disruption approval declaration, positive minimum request, maximum reduction ratio, headroom factor and maximum throttling ratio. Owner mappings are not policies. The rule independently checks scope/freshness, minimum window, per-entity quality, request/usage basis, known autoscalers, OOM, peak/P99 and environment policy. Proposals round upward and obey every policy bound. Neither evidence nor a proposal authorizes a change. Memory, Pod accounting and autoscaler reviews have their own contracts below. PDB selector matching and scheduling simulation are not supplied; preserved metadata is not proof those analyses ran.

## Memory Investigation Evidence

## Memory Request And Limit History

## Memory Safety Readiness

`WorkloadSafetyPolicy.memory` is an optional map keyed by exact container name, defaulting to empty. A CPU policy or another container's policy never supplies memory approval. Each `MemorySafetyPolicy` requires a positive `minimum_request_mib`, a `maximum_reduction_ratio` strictly between zero and one, `headroom_factor >= 1`, and a nonblank `evidence_reference`. Optional positive `startup_peak_mib`/`failover_peak_mib`, a strict nonnegative integer `eviction_events`, and reviewed `qos_class` default to unknown. Nonfinite values, booleans as numbers and fractional/string eviction counts are rejected.

Example entry inside an existing workload safety policy:

```json
{
  "memory": {
    "synthetic-container": {
      "minimum_request_mib": 128,
      "maximum_reduction_ratio": 0.5,
      "headroom_factor": 1.25,
      "evidence_reference": "synthetic-review/memory",
      "startup_peak_mib": 240,
      "failover_peak_mib": 250,
      "eviction_events": 0,
      "qos_class": "Burstable"
    }
  }
}
```

The parent policy's owner, SLO reference, disruption review and exact reviewed UTC window apply to each entry. Startup/failover peaks and eviction counts are explicit owner-reviewed evidence declarations for that container and window, not advisor-collected metrics or inferred event causes. The reference identifies independently approved evidence; it is never fetched, executed or treated as source attestation. Reports label these values `owner-reviewed:<reference>` separately from collected metrics. Missing declarations never become zero or a successful review. This does not add an eviction collector or approve a change.

`WorkloadSnapshot.qos_class` retains a recognized admitted-Pod `status.qosClass` only when all current members explicitly agree; missing, invalid or mixed observations stay null. Do not infer QoS from one container's resources. `ResourceObservation.memory_observation_basis="pod"` is set only for an approved single-Pod roster after complete constant desired/available replica and absent-controller histories, independently observed compatible current controller configuration, and explicitly absent init/runtime overhead. Compatible current configuration permits at most one exact-target Off-mode VPA, but no matching HPA/ScaledObject, invalid evidence or unknown discovery. The current VPA mode is retained, not replaced by a historical absence flag. These checks are independent of CPU usage. Their original controller summaries remain in history evidence. This marker does not itself establish memory usage, request or limit quality; each still needs independent historical evidence.

`AKS-MEM-002` version `1.0.0` consumes these fields for readiness-only review. Stable direct or approved conservative replica-envelope memory history must independently establish positive requests/limits, working-set percentiles/peaks and zero OOM/restarts. Owner-reviewed scenarios/evictions and observed/reviewed Burstable QoS remain mandatory. Collected positive evictions or recent abnormal termination context veto reductions; envelope review additionally requires observed current admission lists and complete workload eviction history. Unsupported overhead, changing request/replica values, active/unknown controllers and invalid identity remain blocked. Full rules are in [metrics and scoring](metrics-and-scoring.md#memory-safety-review).

The rule never computes a target, changes a limit or emits `proposed_requests`; owner bounds are retained as review evidence, not applied as a numeric proposal. A passing informational finding is neither a waste claim nor proof of safe effective-Pod accounting. Snapshot, assessment and collection-plan schemas expose these fields within schema 1.0.

## Memory Request Proposals

`MemorySafetyPolicy.allow_request_reduction` is a strict boolean defaulting to **false**. Omission or false permits readiness review only; null, numeric and string substitutes are rejected. A true value enables evaluation of proposals for that exact container, not cluster mutation, remediation or change approval. Another container's policy never supplies this opt-in.

Independent `AKS-MEM-003` version `1.0.0` requires guarded mode, every memory-readiness/source/identity/time/unit/environment gate plus nonblank owner/SLO and **100% full-grid history** for requests, limits, working-set P95/P99, OOM and restarts. Direct single-Pod history remains supported; approved replica/churn envelopes require complete roster-digest binding, constant request/limit min/max, stable desired/observed/available counts, fresh compatible exact-target controller configuration, observed admission lists and full workload eviction history. These are per-replica maxima before percentiles, not summed/averaged summaries. Known Container LimitRange minima/maxima/limit-request ratios also gate proposals. Unsupported init/runtime/Pod-level resources, changed values and active/unknown controllers stay blocked.

The deterministic safety floor is an upward-rounded whole MiB value bounded by the owner minimum, maximum reduction ratio and headroom around the largest of P99, observed working-set maximum, reviewed startup peak and reviewed failover peak. The upstream candidate must be at least that floor and strictly below the current positive request; an accepted proposal preserves the candidate's value instead of substituting the floor. Rounding that eliminates a possible reduction produces `no_safe_memory_reduction`. The exact formula is in [metrics and scoring](metrics-and-scoring.md#memory-request-proposal).

Eligible findings contain `current_requests.memory_mib` and `proposed_requests.memory_mib`, with CPU fields null and the independently observed unchanged memory limit retained as evidence. They include owner review, validation and explicit restoration of the original request on regression. No limit changes, other-container changes, whole-manifest replacement, automatic rollout, node-removal or financial-savings claim is produced. `AKS-MEM-002` remains informational even when numeric proposals are enabled. All rejected candidates expose blocked reasons without proposed values.

## Restart Investigation Evidence

`ResourceObservation.restart_events` is an optional nonnegative integer in schema 1.0, defaulting to `null`, never zero. It represents a full-window container restart total, not a current lifetime counter or a count of failed Pods.

Approved direct history maps `restarts` with exact workload/Pod identity; approved replica/churn history maps only explicit complete-roster `replica_restarts`. Require a unique issue-free full-grid event summary, recent tail and integral total consistent with interval extrema/counts. Fractional estimates are never rounded. Normalized extrema describe the total; original interval summaries remain replayable. Missing CPU history/current autoscalers do not hide qualified investigations. Missing/foreign/incomplete evidence and unsupported aggregate semantics stay unknown.

`AKS-REL-001` version `1.0.0` also supports the independently approved `replica_restarts` interval-total recording bound to the complete historical roster. Generic per-Pod `restarts` under an envelope identity is not substituted. Exact source/scope/UTC/window/freshness/coverage and integral-counter consistency remain mandatory. Zero produces no finding; incomplete/fractional/foreign counts stay unknown. Counts do not establish an OOM cause, node pressure, application failure or SLO impact. Current termination and collected eviction context are separate rules below.

### Separate Memory Limit Proposal

`WorkloadSafetyPolicy.memory_limits` is an independent exact-container map of `MemoryLimitPolicy`. `allow_limit_reduction` is strict boolean and defaults false. Require a positive owner minimum, maximum reduction ratio `(0,1)`, headroom `>=1`, reviewed positive **total-memory** startup/failover peaks, explicit allocator/cache review, a nonblank evidence reference and `memory_limit_configuration_digest(workload)`. Working set alone cannot substitute; contradictory total/working-set extrema/percentiles block. Known abnormal termination blocks independently.

Current `v1/limitranges` availability plus a successful versioned list are mandatory. Typed admission minima/maxima/limit-request ratios and a digest preserve current Container limits; Pod-level/malformed memory admission constraints stay unsupported. Missing lists remain unknown even after digest resealing. Requests retain their existing direct-history boundary but cannot bypass known admission constraints; new replica-envelope proposals additionally require observed admission lists.

The limit target obeys owner/current admission bounds, stays strictly above the unchanged request and observed/reviewed total-memory peaks, and strictly below the original limit. `current_limits/proposed_limits.memory_mib` are separate from request proposals; combining proposed requests/replicas/limits in one finding is rejected. Limits, requests and other dimensions require separate canaries. Restore the exact original limit on OOM/restart/eviction/SLO regression through customer delivery tooling. Guaranteed/BestEffort, Pod-level resources, init/runtime overhead, replica/churn limit changes and active/unknown controllers remain blocked. Savings stay null. Existing Headlamp views display the dimension but explicitly refuse it through the resource-request approval workflow, including mixed imported records.
