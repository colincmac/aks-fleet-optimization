# Data contracts

## Unified Version

All current models use **schema 1.0**. All 21 rules have packs.
The CPU proposal/review pack `AKS-RQ-002` uses **2.1.0**; eighteen existing
packs use **2.0.0**, and `AKS-SCHED-001`/`AKS-NP-002` use **1.0.0**.
Inputs must use a supported schema and configuration. Unsupported schemas are
rejected. The [JSON schemas](../schemas) are generated by
`scripts/generate_schemas.py`; `--check` detects drift without writing.
JSON Schema alone does not enforce executable scope, projection,
receipt, UTC and cross-field validations.

Every rule ID in `AnalysisReport` must have a manifest, and selected findings
use that manifest's version.
`PackManifest` owns evidence-selected controller `summary_variants` (closed,
evaluator-specific keys) and CPU `baseline_rollback` guidance. These are local
text, not executable expressions. Configuration locks must match installed
manifest and query definitions. When they differ, retain a compatible package
for replay or create a new assessment from reviewed original evidence; never
edit saved hashes to conceal the mismatch.

| Schema | Boundary |
|---|---|
| fleet-snapshot | Normalized deterministic engine input |
| analysis-report | Eligible and blocked findings |
| onboarding-config / readiness-report | Explicit source/scope declarations and offline readiness |
| azure-inventory / kubernetes-metadata / prometheus-metrics | Independent approved collector fragments |
| assessment-fragments / offline-assessment | Unified assembly input and assessment with evidence |
| collection-plan | Explicit bounded collection request |
| recommendation-pack / query-export / analysis-config | Typed pack manifest, scope-bound query export and baseline/guarded selection with integrity locks |
| source-profile / source-capabilities / metric-query-plan | Declared metric shapes, per-source/pack/mode evidence diagnostics and bounded execution cost |
| operator-catalog / operator-inspection / execution-preview | Generated cards/glossary/examples, optional original assessment inspection for Headlamp, and offline CLI operation/query/budget preview |
| cost-import / cost-reconciliation | Separate sanitized amortized-cost projection, exact resource bindings, reviewed allocation shares and decimal currency ledgers; no savings or engine contract changes |
| history-run / history-trend | Separate tenant-bound local run summaries and explicit two-run finding comparisons; no automatic resolution, savings or governance state |

The local history store preserves original assessment artifacts in bounded,
content-addressed local envelopes. Import verifies the original manifest,
tenant/input/snapshot/configuration hashes and locked engine replay. Listing and
comparison validate stored content without substituting current rule definitions.
Original configuration locks must still match installed packs for all commands;
retain compatible package versions for old stores. No cross-version migration
or lock resealing is provided.
Comparison identity includes exact cluster IDs/fingerprints, requested scopes,
configuration, original pack provenance and window duration. Missing findings
remain `not_observed`, explicit ineligible records `blocked`, changed bases
`not_comparable`; no result claims resolution. First/last observed times are
pair-scoped. See [schema, retention and restore boundaries](operations/history.md).

The [offline financial evidence contract](cost-reconciliation.md) is separate
from workload analysis.
Original costs and unmatched rows are retained; charge and attribution are
non-additive views. Declared amortization, exact period/tenant/identity, complete
fresh source evidence and configured allocation coverage are independent gates.
Mixed currencies remain separate and block reconciliation. Reconciled attribution
does not authorize savings.

Operator inspection and preview describe configuration, not observed source facts.
`OperatorCard` groups the manifest, original provenance/effective parameters,
parameter guidance and synthetic baseline selection. `OperatorInspection`
retains a card, assessment mode, capability records and optional resolved queries;
an omitted inspection never implies the current installed pack was used.
The Headlamp import boundary checks pack/version/mode/exact scope and rejects
baseline numeric proposals. Owner checks stay separate; no mode or digest
establishes approval. `ExecutionPreview` records UTC time/window, config/plan
digests, selected pack locks, exact operation/query expressions, collector-planned
counts, limits, excluded fields, configured destination and explicit unresolved
prerequisites. It is not a receipt, evidence of live permissions or a successful
assessment. See the [operator workflow](recommendation-packs.md#operator-workflow).

## Source Profile Evidence

See [source profiles](source-profiles.md). `MetricSourceProfile.catalog_profile`
selects the conservative historical-identity adapter or explicit `cadvisor-ksm`
name-only measurements. Component versions are declarations compared with a
synthetic characterization matrix, not automatic version discovery or
certification. Exports/metric fragments retain the declared source definition.

`MetricEntity(kind="unresolved_container")` requires exact cluster scope,
namespace, Pod name and container, and forbids workload/Pod UIDs or membership/
node claims. `OfflineAssessment.baseline_measurements` retains these summaries
without joining current names into historical workload observations.

`source_capabilities` records available/unavailable/unknown/unsupported checks
per source, cluster, pack and mode with aware UTC evaluation time. Status reflects
all checks. Unsupported declared sources veto numeric proposals; capability
availability does not replace owner, identity, coverage or reliability gates.

`query_plan` describes unique expression/interval bases, planned requests and
expected evaluations. Run-local cache snapshots preserve dependent evidence,
errors and warnings. Total evaluation budgets and per-response series limits are
explicit; missing data and response excess never become zero. Replayed snapshots
retain original capability/profile evidence, not inferred current compatibility.

## Pack Selection And Replay

All 21 rules have closed typed evaluators and manifests, including
eight memory/reliability packs. Memory policies
remain owner-only bounds; these packs forbid ratio parameters. Current accounting
and termination are inventory-only. OOM/restart, memory usage/request/limit,
replica-envelope and workload reliability/controller references share packaged
query assets with explicit MiB/events/pods/boolean units.

`RuleAssessment` retains each rule's own required metrics, quality map, evidence,
reason codes and signal. Shared scope/quality gates remain outside family
algorithms. Unsupported source-profile checks apply to numeric proposals, and
baseline still rejects any numeric proposal. Source/wheel replay preserves the
exact original request/limit/accounting shapes; no schema compatibility reader
or source attestation is introduced.

Manifests use closed evaluator/family/evidence bindings.
`PackParameters.review_ratio` is required
only by CPU request review, CPU request risk and pool review, with their own
finite bounds. Inventory and memory/reliability evaluators forbid a ratio;
memory proposal bounds belong to owner policy. Inventory manifests declare no
transports or queries. Metric manifests
require nonempty entity-specific dependencies for both modes and all manifests
require explicit operator actions/validation/rollback.

Missing request, request risk and pool review use version 2.0.0 and propose
neither resources nor savings. Node query assets retain mCPU/MiB units and exact
historical node identity. Current-only membership or changing capacity remains
unsupported by the existing sum-before-percentile normalization.
The identity-enriched source profile uses version 1.3.0 for node, memory/
reliability, workload guard and HPA history references.
Source capabilities do not pretend that inventory requires Prometheus.

See [recommendation packs](recommendation-packs.md). `AdvisorConfig.mode` defaults
to `baseline`; `guarded` is explicit. Optional `packs` is a nonempty distinct list
of implemented pack IDs; omission evaluates all 21 packs. The scheduling and
capacity inventory packs provide qualified investigations or explicit
missing-context blocks, not numeric proposals. An incomplete
installed catalog is rejected rather than executing an unpacked rule.
Pack parameters are typed, bounded and per-pack.
For CPU request review, configure `pack_parameters.AKS-RQ-002.review_ratio`.

`AnalysisReport` requires mode and selected pack provenance. Its
validator rejects baseline numeric proposals. Provenance includes pack version,
manifest/query digest, parameters and query definitions. `MetricQuality` retains
optional `query_expression` from actual collection; omitted import provenance
stays unknown, never inferred from current definitions.

Artifact exports save effective `pack_locks`; configuration validation and
analysis reject mismatches before live access or evaluation. A hash binds
definitions, not customer source attestation or change approval. Fixed-clock
source/installed-wheel replay uses the same evidence, parameters and assets.

## Snapshot Contract

Preserve exact subscription/cluster/agent-pool Azure IDs and cluster fingerprint, Namespace/workload/Pod/node UIDs. Names are display fields, not substitutes for historical identity. All timestamps must be aware and normalize to UTC. Windows are ordered; numeric values are finite and unit-labelled. Missing, zero and explicitly absent are different states.

`FleetSnapshot.collection_manifest` may be missing only as incomplete evidence: rules then block. `ResourceObservation.cpu_request_observed` defaults false. Omitted HPA/KEDA/VPA/OOM state is unknown, never false/zero. `cpu_observation_basis` must explicitly be `pod` or `replica-envelope` before numeric CPU proposals; unknown aggregation blocks them.

`ResourceObservation.memory_request_observed` and `memory_limit_observed` default false. Values and flags describe current admitted evidence only; historical quality is separate. Unknown, observed absence and observed zero are not interchangeable.

## Scoped Collection Eligibility

Every manifest requires nonempty `source_results` and one `results` aggregate per collector. Aggregates must exactly match deterministic source merges, including clocks, retries, pagination, missing fields, failures and status. Overlapping sources, contradictory completion and missing receipts are rejected. Unknown source clocks stay unknown.

Each `CollectorResult` records nonempty requested scope, completed subset, UTC collection clocks, optional source observation time, pagination, retries, missing fields and sanitized failure codes. Complete requires every requested scope, all pages, no errors and no missing fields. Failed requires an error and no completed scope; incomplete fragments stay partial/failed.

Rules select exactly one complete, fresh, temporally valid matching source for each required collector. Azure matches exact cluster or subscription; Kubernetes and metrics match the exact cluster. Ambiguity blocks. A partial multi-scope receipt cannot be split into successful completed scopes. Optional cost failure does not suppress capacity findings. Global sample/coverage floors are diagnostics; required entity-level quality remains a hard gate. Independent healthy findings can coexist with denial and overall partial status.

## Azure Inventory Composition

`AssessmentFragments.azure` is always a nonempty list of 1 to 1000 `AzureInventorySnapshot` fragments. Each tenant, subscription, cluster, child-pool ID and receipt must match both the profile and that fragment's own scope. Duplicate clusters and overlapping exact/subscription claims fail closed; there is no freshest-wins merge. Missing targets downgrade their claiming receipt; unclaimed targets get failed unknown-clock receipts.

Azure fragments contain observed metadata, not allocatable capacity or workload usage. Unknown pool counts, scaling state, zones, Spot and Fleet membership stay null. ARG completion means the authorized view was paged, not proof of subscription-wide permissions or current ARM state. Source `Date` observations do not prove index refresh time. See [Azure operations](operations/runbook.md#azure-inventory-api).

## Kubernetes Metadata

Metadata carries exact cluster scope, an independently approved `kube-system` Namespace UID fingerprint, API availability/list versions, projected objects, ownership and node-provider reconciliation. The fingerprint is operational binding evidence, not Azure attestation. Export ingestion reruns the collector's allowlist projection and rejects unsupported kinds, attributes, labels or nested fields before persistence.

Approved projections retain requests/limits, init/sidecar/runtime overhead, scheduling constraints, HPA targets, VPA policies/status and PDB details. Typed `OfflineAssessment.metadata_evidence` retains them for later rules without flattening unknowns into booleans. Pod environments/commands/arguments/annotations, Secrets, ConfigMap bodies, logs, private addresses and credential material are excluded. Only named labels are retained; dropped labels are unknown, not absent.

Available APIs need successful versioned lists; absent must be explicitly discovered absent, not denied/unsupported. Ownership follows exact namespace/API/kind/name/UID references through ReplicaSets where applicable. Node-provider joins require approved Azure parent/pool/resource-group bindings. Cross-resource lists are not transactional. The SDK may transiently decode excluded fields before projection; operators requiring a stricter boundary must supply approved sanitized readers/exports. See [Kubernetes operations](operations/runbook.md#kubernetes-metadata-api).

## Current Autoscaler Configuration

Optional `WorkloadSnapshot.autoscaler_configuration` retains a typed `WorkloadAutoscalerConfiguration`, not an arbitrary controller body. It binds exact cluster resource ID/fingerprint, Namespace UID/name, current workload UID and `apps/v1` Deployment/StatefulSet target, observation time and `current_only: true`. Omission remains unknown. Strict `hpa_observed`/`vpa_observed` flags default false; only a discovered-absent API without contradictory objects or an available API with a successful versioned list establishes observation. Complete, fresh scoped source receipts are independently required; flags alone do not prove collection completion.

HPA/VPA target references contain API version, kind and name rather than workload UIDs. Normalization reconciles that exact current target within the observed Namespace to the uniquely listed workload UID; it never invents historical identity from names. Malformed/missing references produce `ambiguous_autoscaler_target`; clearly different namespaces/kinds/names are not matches. This is current configuration intent, not attestation that a controller acted on that UID or that separately listed objects were observed transactionally.

`HpaConfiguration` preserves controller UID/name and explicit `HpaMetricSignal` descriptors for Resource, ContainerResource, External, Pods and Object signals. Resource/container signals distinguish positive integer utilization percentages from positive absolute quantity targets; ContainerResource names the exact admitted container. Missing/defaulted-away metrics, ambiguous target shapes, invalid quantities and unsupported fields remain explicit `unsupported_hpa_configuration`, never an assumed default CPU target. The existing optional quantity parser validates absolute targets during normalization; the rule engine itself uses no Kubernetes/Azure client.

`VpaConfiguration` preserves UID/name, explicit Off/Initial/Recreate/Auto/InPlaceOrRecreate update mode and `VpaContainerPolicy` entries. Mutating modes require explicit container mode and controlled CPU/memory resources; Off does not require mutation policy. Exact-container policies override `*`; duplicate policies, unknown modes/resources and missing policy evidence produce `unsupported_vpa_configuration`, not invented API defaults. Both RequestsOnly and RequestsAndLimits control requests; omitted `controlled_values` does not become a claim about limits. The collector now allowlists nonsensitive `mode` and `controlledValues` fields alongside existing VPA policy fields, without new permissions or collecting arbitrary configuration.

`AKS-AS-002` version `2.0.0` consumes this snapshot evidence for a current-only interaction review. It joins observed HPA utilization signals with mutating VPA policies on the same workload, exact container and CPU/memory resource. Absolute/external signals, Off VPA/container mode and disjoint resources do not establish this request-denominator risk. Unknown APIs, incomplete policy, stale/future/mismatched bindings or incomplete sources remain blocked. See [rule semantics](metrics-and-scoring.md#current-autoscaler-interaction).

The rule requires no Prometheus or historical coverage and makes no historical/runtime claim. KEDA-owned HPAs are evaluated by their observed HPA signal, never by assuming trigger semantics or treating ownership as a second HPA. Current positive/unknown controller evidence blocks contradictory absence claims for CPU/memory reductions. The fixed-replica review cannot claim no HPA when one is observed or treat unknown current configuration as proven absence. Snapshot and assessment schemas expose this evidence within schema 1.0; approved original projections remain in `metadata_evidence`.

HPA configuration also retains optional explicit `min_replicas`, `max_replicas`, `current_replicas` and `desired_replicas` from admitted spec/status. Omission stays null, not the Kubernetes default or today's workload count. Counts are strict nonnegative integers (maximum must be positive); known minimum cannot exceed known maximum. These current fields alone do not prove historical bounds or pinning.

## Historical Metrics

`PrometheusMetricsSnapshot` stores identity-bound summaries, query version, UTC range/step, quality, latest sample time and receipt. No raw samples, arbitrary labels, endpoints or credentials are persisted. Containers require exact workload/Pod UID and container name; workloads retain exact UID; nodes require exact resource ID/UID. `workload_container` represents an approved historical aggregate with container identity and `membership_digest`, never a fabricated Pod UID.

Configured cluster/namespace/workload/container mappings plus canonical historical UID labels must exist in the source. Missing enrichment/recordings do not fall back to name-only joins. `aks_advisor:*` recordings are explicit upstream contracts, not assumed built-in AKS features. No recordings are installed or backfilled by the advisor.

Gauges use aligned `[start,end)` evaluation points; counter increases use disjoint complete intervals ending through `end`. Missing/warned/incomplete counter totals remain null. Percentiles use inclusive interpolation over collected aligned samples, never averages/sums of percentiles. Coverage measures returned evaluation points, not raw scrape completeness or absence of intra-step bursts. Missing/invalid/off-grid/duplicate/stale evidence is explicit. Unknown service time is not processing time.

Per-metric quality checks source/query, units, window, resolution, count/coverage consistency, extrema and freshness. Default observation minimum is 30 days and maximum step 300 seconds; approved explicit analysis configuration may tighten/change supported policy bounds. Current data never extends missing history. See [metrics operations](operations/runbook.md#prometheus-metrics-api).

## Historical HPA Replica Bounds

`MetricEntity(kind="hpa")` requires exact cluster resource ID, Namespace/workload kind/name/UID and canonical `hpa_uid`. HPA history cannot claim Pod/container, node or membership-digest identity; other entity kinds cannot claim `hpa_uid`. HTTP projection, selectors, label-collision checks and collection plans retain this explicit controller identity. Display names do not substitute for either UID.

Four optional query keys select approved `aks_advisor:hpa_min_replicas`, `aks_advisor:hpa_max_replicas`, `aks_advisor:hpa_desired_replicas` and `aks_advisor:hpa_current_replicas` gauges, in pods. The producer must preserve the HPA UID and its historical target workload UID at each point, not relabel old data using today's target. These are upstream contracts, not assumed built-in kube-state-metrics/AKS recordings; the advisor never installs, backfills or zero-fills them.

Optional `WorkloadAssessmentBinding.hpa_uid` explicitly binds this controller to the existing approved scope/source/history reference and reviewed UTC window. The Pod roster and today's metadata cannot supply HPA history. An omitted controller binding stays unknown. `WorkloadSnapshot.hpa_replica_history` separately retains `HpaReplicaHistory` with exact cluster/fingerprint/Namespace/workload/HPA identities, source/query/reference and per-gauge `HpaReplicaMetric` extrema/quality. Original source summaries remain in `WorkloadHistoryEvidence`. The current-only configuration is not converted into historical evidence.

Normalization requires unique, structurally consistent, identity-matching summaries and integer nonnegative count extrema; fractional counts are not rounded. Partial valid quality remains explicit for rule gating, while malformed/foreign/missing summaries stay unsupported/unknown. Duplicate metric observations are rejected by the existing assessment import boundary. Raw source references remain untrusted text and are never fetched or treated as attestation.

`AKS-AS-003` version `2.0.0` requires one current HPA, matching identities, complete fresh source receipts, configured observation duration, full-grid 100% aligned history for all four gauges, source/query/unit/resolution/freshness consistency, constant historical bounds matching current bounds, and matching current HPA desired/current and workload replica counts. Desired/current extrema must both be constant at the floor or ceiling; equal floor/ceiling is reported once as `fixed`. Changing/recreated/multiple-controller histories or changed current context remain blocked; varying valid replica counts produce no pinned finding. VPA policy/CPU usage are not prerequisites.

The rule reports sampled bound history only, never a safe minimum, demand/saturation diagnosis, replica target, controller change or savings. Historical HPA evidence also vetoes contradictory vertical reductions without suppressing independently eligible OOM/restart context. The separate explicitly opted-in proposal below does not change `AKS-AS-003` eligibility. Zero-replica onboarding remains unsupported.

## Autoscaler Assessment Completion

All seven autoscaler rules use version 2.0.0 packs and closed typed evaluators.
Current reviews
are inventory-only; sampled history and the guarded floor proposal consume
shared packaged queries with separate HPA/workload identity. Pack locks bind
manifests and query assets; mismatched locks fail explicitly. These contracts
do not grant permissions or authorize mutations.

- `WorkloadAutoscalerConfiguration.keda_observed` requires successful versioned discovery/lists for both ScaledObjects and ScaledJobs, or explicit API absence. `kedas` contains only supported ScaledObjects targeting the uniquely observed Deployment/StatefulSet through explicit `apps/v1` kind/name references. Missing/defaulted target fields remain ambiguous, not inferred.
- `KedaConfiguration` retains exact UID/name, trigger type and optional explicit metric type, min/max replicas, polling/cooldown seconds and current `status.hpaName`. Trigger metadata, activation thresholds, authentication references/values and credentials remain excluded. The collector retains only the nonsensitive HPA name from this status context.
- `HpaConfiguration.owner_references` retains typed API/kind/name/UID/controller references. `AKS-AS-004` requires the generated HPA name and exactly one matching controller owner. A ScaledObject and its generated HPA are one scaling chain, not two HPAs. Missing or mismatched ownership stays blocked; multiple independent controllers are an investigation.
- VPA policies retain optional parsed `min_allowed`/`max_allowed`; recommendation status retains per-container target/lower/upper/uncapped CPU mCPU and memory MiB values. Invalid supplemental bounds/status produce independent `evidence_issues`, preserving an otherwise valid `AKS-AS-002` denominator investigation. `AKS-AS-007` requires unique matching containers and explicit consistent resource/policy bounds. Status observation does not attest recommendation generation time, and this rule never proposes resources.
- `AKS-AS-006` investigates valid sampled changing bounds/counts or changed fresh current bound/status context. It does not infer oscillation, controller instability, scaling lag or unmet demand. Wrong/recreated identities, multiple historical controller bindings and incomplete histories still block numeric proposals.

### Opt-In Replica Floor Proposal

Optional `WorkloadSafetyPolicy.replicas: ReplicaSafetyPolicy` is default-off through strict boolean `allow_floor_reduction`. It binds an exact `hpa_uid`, positive `minimum_available_replicas` and `tested_replicas`, maximum reduction ratio, explicit nonnegative failover reserve and maximum-unavailable allowance, and an opaque evidence reference. Peak-load, startup, throughput, zone-failure and reliability reviews must all explicitly be true; owner-reviewed OOM/restart/eviction counts must all explicitly be zero. These counts and references are **owner declarations**, not collected measurements, source attestation or approval.

`configuration_digest` must equal `replica_configuration_digest(workload)`, exported in the `AKS-AS-003` evidence. It binds exact scope/workload/HPA identities, current HPA configuration, normalized requests/limits and a digest of every current admitted Pod UID and approved Pod spec projection. It excludes clocks, HPA status and the policy itself. A digest proves integrity only; operators must independently verify that the referenced load/availability review tested this configuration at `tested_replicas`. Material Pod/HPA changes require a new review; no reference is fetched.

`HpaReplicaHistory.workload_metrics` independently retains exact workload-UID desired/observed/available replica extrema and quality from existing catalog series. `availability_issues` and `reliability_issues` are independent of the four HPA gauge histories. Original summaries remain replayable; current counts never backfill history. Valid identity-bound positive OOM/restart history vetoes contradictory owner zero declarations; missing metrics do not become zero.

`AKS-AS-005` requires all existing HPA/source/window/identity/freshness gates, a stable sampled **floor** with unchanged bounds/status, and 100% aligned evaluation points for all seven HPA/workload replica series. Workload desired/observed/available counts must remain constant at the current replica count, with matching current Deployment `availableReplicas`. It additionally requires a reviewed environment, nonblank owner/SLO/reference, an exactly reviewed window and disruption review.

Only unconstrained homogeneous current **Deployments** with one unmanaged HPA and no KEDA or mutating VPA are supported. Explicit empty `initContainers: []` and `overhead: {}` are required; missing/null fields remain unknown even if an owner supplies a matching digest. PDB matching, StatefulSet/quorum floors, scheduler/affinity/selectors/tolerations/topology constraints, volumes/local state, priority/runtime classes, init/sidecar overhead, changed/recreated/multiple-controller histories and scale-to-zero proposals remain explicitly blocked, not silently accepted. Optional native snapshot constraint/Pod-configuration evidence defaults unknown. Current inventories with PDBs already remain normalization gaps.

Findings contain paired positive integer `current_replica_floor` and strictly lower `proposed_replica_floor`; resource-request changes cannot coexist with a replica proposal. Maximum replicas, HPA signals, CPU/memory and other workloads are unchanged. Savings remain null. Reports require separate owner approval, isolated canary validation and restoration of the exact original floor on regression. Existing Headlamp views display these fields, but their resource-request approval workflow explicitly refuses replica-floor proposals, including mixed imported records.

## Current Placement And Capacity Investigations

`ClusterSnapshot.scheduling` retains the exact cluster/fingerprint, observation
time, per-Pod Namespace/controller identities, typed observed constraint counts,
unobserved fields, namespace PDB candidate UIDs, tainted/cordoned Node UIDs,
DaemonSet UIDs and explicit issues. Normalization uses admitted Pods and exact
owner chains independently of vertical workload eligibility, so a PDB or missing
request history does not erase current placement evidence. Deployment,
StatefulSet, DaemonSet and Job owner chains need versioned complete lists;
unresolved owners, malformed fields and missing identities remain blocked.
Hard/soft affinity and topology are distinct. Tolerations are permissions, not
pinning. Volume references are not volume/CSI binding facts. Missing projected
labels cannot prove matches, and namespace PDB candidates are not matched
budgets or an availability assessment.

`ClusterSnapshot.capacity` independently retains nullable ARM pool facts,
Azure/Kubernetes observation times, current provisioning mode, versioned NAP
API status, summarized NodePool/node-class configuration completeness and
provider/UID-bound NodeClaim supply. Only exact current NodeClaim owner
API/kind/name/UID plus one provider-bound Node with independently reconciled Azure
scope establishes observed NAP supply. Cluster Auto mode does not imply an ARM
pool is NAP-managed. Missing API versions, ownership, node-class or provider
bindings remain unknown/issues, not absence or eligibility.

Optional `AssessmentFragments.pool_intents` bind exact cluster/pool resource IDs
to nonblank owner/reference and `specialized` or `intentionally-reserved`
classification. Duplicate/foreign bindings are rejected, including native
snapshot intent mismatches. Declarations are untrusted review context, not
attestation or change approval; references are never fetched. SKU names and
equal CAS bounds do not infer specialization or owner intent.

Both packs require fresh complete scoped Azure/Kubernetes receipts and coherent
snapshot observation times, not metric duration/coverage. Missing native
inventory is explicitly blocked. Original snapshots/fragments and selected pack
locks reproduce reports offline. Omitted current-evidence fields remain unknown;
missing evidence is never synthesized for compatibility.
These packs never produce resource/count proposals, packing or savings.
Networking, identity, quota/SKU availability, disruption/workload fit and
stop/start/egress acceptance require independent evidence before any NAP
eligibility or migration claim. Existing vertical guards are unchanged.

## Offline Pool Normalization

Require Manual provisioning, observed pool metadata, exact current and approved historical node membership, constant full-window `mCPU`/`MiB` allocatable totals agreeing with node totals, and aligned sum-before-percentile pool CPU usage. Pool capacity is a total, not a per-node value. Never substitute current allocatable values, sum percentiles, extrapolate survivors or invent count/mode/Spot flags. NAP, churn and changing capacity remain explicit unsupported cases, not removable-node or savings claims.

## Current Workload Inventory

Support `apps/v1` Deployment/StatefulSet with 1 to 100 declared replicas, exactly that many distinct Running v1 admitted Pods, exact Namespace/controller chains, versioned APIs and conservative PDB evidence. Every Pod must have identical normalized container names, CPU requests, memory requests/limits and observation states. Mixed/currently incomplete populations stay unsupported rather than being represented by one arbitrarily selected Pod. Evidence retains every current Pod UID deterministically as `current_only`; Running does not imply readiness or historical membership.

Requests come from admitted Pods, never templates. Explicit empty requests/null CPU establishes observed absence; omitted requests remain unknown. Present string quantities use `kubernetes.utils.quantity.parse_quantity`, lazily loaded from the optional extra, converted from cores to mCPU. Invalid, negative, nonfinite, overflowing and underflowing values fail closed. Parser absence is a gap. Inventory alone may support missing-request investigations, but cannot supply usage, autoscaler absence or owner policy.

Memory requests and limits use the same quantity parser, converting bytes to MiB (1 MiB = 1,048,576 bytes). Binary/decimal suffixes and exponent notation retain their standard meanings. An explicit resources `requests`/`limits` map with an omitted or null memory entry establishes observed absence (`true` flag, null value), not zero. Omitted maps remain unknown (`false` flag); explicit zero is retained as zero. Malformed, negative, nonfinite, overflowing or underflowing memory quantities leave that memory field unknown without fabricating a value or discarding valid CPU evidence. No admission defaults or values from templates are inferred.

## Single-Pod History

`workload_assessments` binds tenant, exact cluster/fingerprint, Namespace/workload identities, a duplicate-free `pod_uids` historical roster, source, history reference and explicit `WorkloadSafetyPolicy`. Bindings cannot transfer to recreated identities. Current members must be in the historical roster. References are not fetched/executed; they and policy are declarations, not source attestation or change approval.

For exactly one current replica and one historical Pod, consume that Pod's issue-free CPU percentiles/extrema, request history, maximum throttling and complete zero OOM interval total. Desired/available replicas and request must be constant across the full aligned grid. HPA/KEDA/VPA histories must explicitly be zero and independent successful current API evidence must prove absence. All current Pods need explicit empty initContainers/overhead and null runtimeClassName. Missing evidence is not absence.

## Replica Envelope History

For multiple replicas or a churned historical roster, require approved upstream `workload_container` recordings. Their `membership_digest` is SHA-256 of canonical sorted JSON containing cluster resource ID/fingerprint, Namespace UID, workload UID and sorted historical Pod UIDs. Every aggregate selector carries that digest. The roster includes deleted members; current Pods alone cannot establish it. Digest/reference assertions require an approved producer and do not cryptographically attest source completeness.

| Catalog Key | Required upstream meaning |
|---|---|
| replica_cpu_envelope | Aligned maximum CPU mCPU across the approved roster at each point |
| replica_cpu_request_min / replica_cpu_request_max | Minimum/maximum observed request across active members, both constant at the current admitted request |
| replica_cpu_throttling | Aligned maximum per-container throttling ratio across members |
| replica_oom_events | Complete per-step OOM increase across members, zero required |
| observed_replicas | Explicit observed member count, constant at declared desired/available replicas |

The collector computes percentiles from aligned **maximum-replica-envelope samples**. These are conservative per-replica upper-envelope statistics, not actual workload-total percentiles or averages of Pod summaries. Full aligned coverage, current homogeneous requests, exact digest, stable observed/desired/available count, complete controller histories and independent current absence are mandatory. Request/replica changes, mixed identity and unsupported lifecycle semantics stay blocked; no survivor extrapolation or automatic time-segmentation is attempted.

## Workload Safety Policy

Numeric CPU reductions require owner, SLO reference, exact reviewed UTC window, disruption approval declaration, positive minimum request, maximum reduction ratio, headroom factor and maximum throttling ratio. Owner mappings are not policies. The rule independently checks scope/freshness, minimum window, per-entity quality, request/usage basis, known autoscalers, OOM, peak/P99 and environment policy. Proposals round upward and obey every policy bound. Neither evidence nor a proposal authorizes a change. Memory, Pod accounting and autoscaler reviews have their own contracts below. PDB selector matching and scheduling simulation are not supplied; preserved metadata is not proof those analyses ran.

## Memory Investigation Evidence

`AKS-MEM-001` version `2.0.0` investigates positive OOM counts; it never proposes memory request/limit values. Unknown counts/quality or missing identity, scope, freshness, resolution, duration or coverage produce blocked findings. Valid zero counts produce no OOM finding. CPU evidence and absent autoscalers are not prerequisites for a memory reliability investigation.

With an existing approved workload binding, normalization independently retains complete direct single-Pod or digest-bound replica OOM counters even when CPU history is unsupported or guarded. A total must be integral and consistent with interval extrema and full-window sample count. Normalized `memory_oom_events` quality extrema describe the full-window total; original interval extrema and totals remain unchanged in `WorkloadHistoryEvidence`. The presence of history evidence is not proof of CPU reduction eligibility. Current controller absence and all other CPU guards remain mandatory for reductions.

Complete aligned direct single-Pod `memory_usage` or approved complete-roster `replica_memory_envelope` summaries may supply optional working-set P95/P99 and observed peaks with `MiB` quality. Missing or invalid optional context does not hide a valid OOM finding and is not shown as zero. Envelopes describe aligned per-replica maxima, not workload totals; unbound replica/churn aggregates remain unsupported. Request/limit history and separately opted-in numeric proposals follow the narrower contracts below.

## Memory Request And Limit History

Approved direct single-Pod history can independently retain `memory_request` and `memory_limit` observations from the existing catalog. Each summary must be unique, issue-free, full-grid, aligned, in MiB, bound to the exact historical identities and constant at the explicitly observed current admitted value. Gauge evaluation ends at `end - step`; missing tail samples do not become complete history. Absent/current-only, changing, mismatched, partial or foreign evidence supplies no historical quality for that field. Current values remain current rather than being overwritten from the historical summary.

Validated summaries populate `metric_quality.request_memory_mib` or `limit_memory_mib` and remain unchanged in `WorkloadHistoryEvidence`. The two fields are independent; CPU quality cannot establish either. Existing binding, Namespace/workload/Pod identities and reviewed-window checks remain required. Approved complete-roster envelopes additionally retain constant replica request/limit min/max matching admitted values under the [recording contract](#replica-memory-and-reliability-recordings); unbound churned rosters and generic replica aggregates remain unsupported. OOM reports include the values only when current observation flags and the existing per-metric scope/freshness/coverage gates pass. Current-only values stay in the snapshot without being presented as historical evidence.

These observations alone support investigation, not a safe memory target. Readiness and request proposals have separate owner guards. The additional limit-only rule below requires full-memory usage and independent explicit opt-in; working set alone cannot authorize it. Savings remain null and schema remains 1.0.

## Memory Safety Readiness

`WorkloadSafetyPolicy.memory` is an optional map keyed by exact container name, defaulting to empty. A CPU policy or another container's policy never supplies memory approval. Each `MemorySafetyPolicy` requires a positive `minimum_request_mib`, a `maximum_reduction_ratio` strictly between zero and one, `headroom_factor >= 1`, and a nonblank `evidence_reference`. Optional positive `startup_peak_mib`/`failover_peak_mib`, a strict nonnegative integer `eviction_events`, and reviewed `qos_class` default to unknown. Nonfinite values, booleans as numbers and fractional/string eviction counts are rejected.

Example entry inside an existing workload safety policy:

```json
{
  "memory": {
    "synthetic-container": {
      "minimum_request_mib": 128,
      "maximum_reduction_ratio": 0.5,
      "headroom_factor": 1.25,
      "evidence_reference": "synthetic-review/memory",
      "startup_peak_mib": 240,
      "failover_peak_mib": 250,
      "eviction_events": 0,
      "qos_class": "Burstable"
    }
  }
}
```

The parent policy's owner, SLO reference, disruption review and exact reviewed UTC window apply to each entry. Startup/failover peaks and eviction counts are explicit owner-reviewed evidence declarations for that container and window, not advisor-collected metrics or inferred event causes. The reference identifies independently approved evidence; it is never fetched, executed or treated as source attestation. Reports label these values `owner-reviewed:<reference>` separately from collected metrics. Missing declarations never become zero or a successful review. This does not add an eviction collector or approve a change.

`WorkloadSnapshot.qos_class` retains a recognized admitted-Pod `status.qosClass` only when all current members explicitly agree; missing, invalid or mixed observations stay null. Do not infer QoS from one container's resources. `ResourceObservation.memory_observation_basis="pod"` is set only for an approved single-Pod roster after complete constant desired/available replica and absent-controller histories, independent successful current controller absence, and explicitly absent init/runtime overhead. These checks are independent of CPU usage. Their original controller summaries remain in history evidence. This marker does not itself establish memory usage, request or limit quality; each still needs independent historical evidence.

`AKS-MEM-002` version `2.0.0` consumes these fields for readiness-only review. Stable direct or approved conservative replica-envelope memory history must independently establish positive requests/limits, working-set percentiles/peaks and zero OOM/restarts. Owner-reviewed scenarios/evictions and observed/reviewed Burstable QoS remain mandatory. Collected positive evictions or recent abnormal termination context veto reductions; envelope review additionally requires observed current admission lists and complete workload eviction history. Unsupported overhead, changing request/replica values, active/unknown controllers and invalid identity remain blocked. Full rules are in [metrics and scoring](metrics-and-scoring.md#memory-safety-review).

The rule never computes a target, changes a limit or emits `proposed_requests`; owner bounds are retained as review evidence, not applied as a numeric proposal. A passing informational finding is neither a waste claim nor proof of safe effective-Pod accounting. Snapshot, assessment and collection-plan schemas expose these fields within schema 1.0.

## Memory Request Proposals

`MemorySafetyPolicy.allow_request_reduction` is a strict boolean defaulting to **false**. Omission or false permits readiness review only; null, numeric and string substitutes are rejected. A true value enables evaluation of proposals for that exact container, not cluster mutation, remediation or change approval. Another container's policy never supplies this opt-in.

Independent `AKS-MEM-003` version `2.0.0` requires guarded mode, every memory-readiness/source/identity/time/unit/environment gate plus nonblank owner/SLO and **100% full-grid history** for requests, limits, working-set P95/P99, OOM and restarts. Direct single-Pod history remains supported; approved replica/churn envelopes require complete roster-digest binding, constant request/limit min/max, stable desired/observed/available counts, fresh current controller absence, observed admission lists and full workload eviction history. These are per-replica maxima before percentiles, not summed/averaged summaries. Known Container LimitRange minima/maxima/limit-request ratios also gate proposals. Unsupported init/runtime/Pod-level resources, changed values and active/unknown controllers stay blocked.

The deterministic target is an upward-rounded whole MiB value bounded by the owner minimum, maximum reduction ratio and headroom around the largest of P99, observed working-set maximum, reviewed startup peak and reviewed failover peak. It must remain strictly below the current positive request; rounding that eliminates the reduction produces `no_safe_memory_reduction`. The exact formula is in [metrics and scoring](metrics-and-scoring.md#memory-request-proposal).

Eligible findings contain `current_requests.memory_mib` and `proposed_requests.memory_mib`, with CPU fields null and the independently observed unchanged memory limit retained as evidence. They include owner review, validation and explicit restoration of the original request on regression. No limit changes, other-container changes, whole-manifest replacement, automatic rollout, node-removal or financial-savings claim is produced. `AKS-MEM-002` remains informational even when numeric proposals are enabled. All rejected candidates expose blocked reasons without proposed values.

## Restart Investigation Evidence

`ResourceObservation.restart_events` is an optional nonnegative integer in schema 1.0, defaulting to `null`, never zero. It represents a full-window container restart total, not a current lifetime counter or a count of failed Pods.

Approved direct history maps `restarts` with exact workload/Pod identity; approved replica/churn history maps only explicit complete-roster `replica_restarts`. Require a unique issue-free full-grid event summary, recent tail and integral total consistent with interval extrema/counts. Fractional estimates are never rounded. Normalized extrema describe the total; original interval summaries remain replayable. Missing CPU history/current autoscalers do not hide qualified investigations. Missing/foreign/incomplete evidence and unsupported aggregate semantics stay unknown.

`AKS-REL-001` version `2.0.0` also supports the independently approved `replica_restarts` interval-total recording bound to the complete historical roster. Generic per-Pod `restarts` under an envelope identity is not substituted. Exact source/scope/UTC/window/freshness/coverage and integral-counter consistency remain mandatory. Zero produces no finding; incomplete/fractional/foreign counts stay unknown. Counts do not establish an OOM cause, node pressure, application failure or SLO impact. Current termination and collected eviction context are separate rules below.

## Memory Completion Contracts

### Replica Memory and Reliability Recordings

The additional optional catalog keys are `replica_memory_envelope`, `replica_memory_request_min/max`, `replica_memory_limit_min/max`, `replica_restarts`, `evictions` and `memory_total_usage`. The envelope gauges use `aks_advisor:workload_container_memory_*_mib` recordings with exact workload/container identity and complete `membership_digest`, including deleted Pods. The producer takes the aligned maximum across replicas before the advisor calculates percentiles. Request/limit min and max must both be constant at the current admitted value; missing maxima never imply stability.

`replica_restarts` uses approved disjoint `aks_advisor:workload_container_restart_increase` intervals, selected with `step_seconds`, over that same roster. `evictions` uses disjoint `aks_advisor:workload_eviction_increase` intervals with historical workload UID; it is a workload total, not a container count. Integral complete totals and original interval summaries are retained. No recording is installed/backfilled, current names cannot reconstruct historical identities, and source references/digests are not attestation.

`ResourceObservation.memory_observation_basis="replica-envelope"` and `memory_membership_digest` are set only after independent full stable controller history and current absence/overhead checks. CPU usage is not a prerequisite. `WorkloadSnapshot.eviction_events/eviction_quality` preserve explicit missing-versus-zero evidence; `AKS-REL-003` reports positive validated evictions once per workload. Positive collected evictions veto contradictory owner zero declarations and CPU/memory reductions.

### Effective Pod and Termination Context

`pod_memory_accounting` retains each current Pod UID, observation clock, application/restartable-sidecar request sum, sequential initialization peak, overhead and effective request in MiB. `AKS-MEM-004` reports current scheduler accounting only: `max(application + all restartable init requests, each regular-init request + previously started restartable init requests) + overhead`. Restartable init startup peaks are also considered. Missing admitted requests/init/overhead, malformed quantities, unsupported Pod-level resource budgets or nonfinite totals remain explicit issues, not zero. This informational rule does not calculate usage, historical capacity, Pod limits or removable nodes; numeric proposals still block init/runtime overhead.

Pod status projection adds only `containerStatuses.name` and `lastState.terminated.reason/exitCode/finishedAt`. Messages, logs, command/environment values and arbitrary termination bodies remain excluded. Exact current Pod/container identity and causal UTC clocks bind `termination_context`; malformed/duplicate/foreign context stays unknown. `AKS-REL-002` reports the retained last termination, never the cause of every restart. Exit code 137 alone is not proof of OOM. Recent abnormal context or invalid current context blocks memory reductions; no historical count is fabricated.

### Separate Memory Limit Proposal

`WorkloadSafetyPolicy.memory_limits` is an independent exact-container map of `MemoryLimitPolicy`. `allow_limit_reduction` is strict boolean and defaults false. Require a positive owner minimum, maximum reduction ratio `(0,1)`, headroom `>=1`, reviewed positive **total-memory** startup/failover peaks, explicit allocator/cache review, a nonblank evidence reference and `memory_limit_configuration_digest(workload)`. The digest binds current scope/workload/Pod/HPA settings, QoS and current admission configuration; references are never fetched and do not attest a load test.

`AKS-MEM-005` requires one stable direct Pod, observed Burstable QoS, current positive requests/limits matching full constant history, complete total-memory usage (`container_memory_usage_bytes`, MiB), zero full-grid OOM/restarts/workload evictions, current absent/inactive autoscalers, reviewed owner/SLO/window/disruption/environment and 100% aligned source/query/quality. Working set alone cannot substitute; contradictory total/working-set extrema/percentiles block. Known abnormal termination blocks independently.

Current `v1/limitranges` availability plus a successful versioned list are mandatory. Typed admission minima/maxima/limit-request ratios and a digest preserve current Container limits; Pod-level/malformed memory admission constraints stay unsupported. Missing lists remain unknown even after digest resealing. Requests retain their existing direct-history boundary but cannot bypass known admission constraints; new replica-envelope proposals additionally require observed admission lists.

The limit target obeys owner/current admission bounds, stays strictly above the unchanged request and observed/reviewed total-memory peaks, and strictly below the original limit. `current_limits/proposed_limits.memory_mib` are separate from request proposals; combining proposed requests/replicas/limits in one finding is rejected. Limits, requests and other dimensions require separate canaries. Restore the exact original limit on OOM/restart/eviction/SLO regression through customer delivery tooling. Guaranteed/BestEffort, Pod-level resources, init/runtime overhead, replica/churn limit changes and active/unknown controllers remain blocked. Savings stay null. Existing Headlamp views display the dimension but explicitly refuse it through the resource-request approval workflow, including mixed imported records.

## Collection Plan And Artifacts

`CollectionPlan` selects exact approved targets/fingerprints, optional sanitized metadata export paths (relative to plan), explicit historical entities/catalog keys, window, step and run budgets. The default window is the last configured complete UTC days. Both bounds or neither are required. No plan endpoint implies consent. The CLI requires `--allow-live`, sanitized exports and supported generic anonymous/public-Azure managed identity transports; it never loads kubeconfig/plugins or bearer environment values. The library accepts approved injected credential/Kubernetes readers.

Collection is sequential (concurrency 1), with per-run bounded reads, objects, query chunks and cooperative elapsed deadline. Defaults: 2000 reads, 50000 objects, 10000 queries, 600 seconds. Hard caps: 10000 reads, 1000000 objects, 100000 queries, 3600 seconds, 100 targets and 10000 entities. Collectors use no retries and at most 20 pages per list; transports keep independent size/timeout limits. Deadline checks do not forcibly interrupt an injected call. Exhaustion leaves honest failure/partial receipts.

Input JSON and total CLI metadata export files are bounded at 32 MiB. `assess --artifacts` exclusively creates a directory under an existing parent, with fixed `fragments.json`, `snapshot.json`, `analysis-config.json`, `assessment.json`, `report.md` and `manifest.json`. Manifest is last and hashes exact UTF-8 bytes of the other files. Failed writes leave no commit manifest; discard/quarantine incomplete directories rather than using them as success. Paths are not derived from untrusted names. Existing output is never overwritten. Storage ACLs/encryption/retention are the operator's responsibility; reports still contain classified workload metadata.

## Recommendation And Replay

Findings retain stable identity-aware ID, rule/version, exact scope, severity/confidence, unit/source evidence, owner/current/proposed values, prerequisites, risks, validation/rollback and nullable savings/currency. Blocked findings retain reason codes but no actionable proposal. The separate offline cost adapter reconciles attribution only; estimated savings remain null, including after reconciliation. Any avoidable billable-resource change, overlap-free forecast or realized financial outcome requires independent customer validation outside this adapter.

Assessments contain input/profile digests, snapshot/report, normalization issues, current inventory, consumed history and sanitized metadata evidence. Profile digests exclude report destination. Engine digests bind snapshot and analysis configuration. These SHA-256 hashes are integrity/replay identifiers, not signatures. Fix `--as-of` for reproducible freshness; `analyze` of exported snapshot/configuration reproduces the embedded report. JSON is untrusted display data; Markdown escapes it. Empty recommendations never mean a healthy fleet.
